> 在 v0.1 设计方案基础上，按 MCP 实测结果和 03 号文档的分析修订。

## 1. 基础工作流程（画风 LoRA）

| 阶段 | 内容 | 执行 | 人工节点 |
|---|---|---|---|
| S0 初始化 | 建 run：画风 tag 串、触发词、目标张数、覆盖矩阵、生成参数快照 | CLI / 前端 | **矩阵与配比定稿** |

```

└──────┬────────┴─────────┬─────────────┴──────┬────────┘
       │                  │ HTTP(127.0.0.1+token) │ MCP(薄封装，后期)
┌──────▼──────────────────▼────────────────────▼────────┐
│ 应用服务层 (FastAPI + 任务队列 jobs 表)                │
├────────────────────────────────────────────────────────┤
│ 流水线核心：stages/ S0–S6，每阶段幂等                  │
│ profiles/：style（第一版）│ character（预留）          │
├───────────┬───────────┬───────────┬───────────┬────────┤
│ManifestRepo│ImageBackend│ VisionTools│ LLMClient │Exporter│
│ (SQLite)   │ Launcher   │ hash/tagger│ 角色→模型 │txt对   │
│            │ MCP(实现)  │ /aesthetic │ 路由      │kohya…  │
│            │ NAI直连(预留)│          │           │(预留)  │
│            │ ComfyUI(预留)│          │           │Trainer │
│            │            │           │           │(预留)  │
└───────────┴───────────┴───────────┴───────────┴────────┘
```

和 v0.1 的主要差别：

- v0.1 是「三个 MCP server + agent 编排」，v0.2 改成「Python 核心库 + 服务层，agent 和前端都是客户端」。MCP server 只是对服务层的薄封装，后期再做。理由：可测试、agent 不可用时也能跑、前端和 agent 共用一套逻辑。
- 生成参数改为 run 级设置（Launcher 不支持按请求传 model/sampler）。
- 画风 tag 被覆盖的风险实测不成立，降级为校验项。

技术栈：Python 3.11+、SQLite、httpx（MCP 客户端）、FastAPI、Pillow/imagehash、前端 Vite + React + TypeScript。

## 2.1 生成参数的接口设计（按 2026-10-12 决议）

约束：Launcher MCP 的 `prepare_generation` 不接受 model / sampler / steps / cfg，这些只能通过 `update_generation_settings` 写页面设置。

抽象方式：我们这一侧统一用 `GenerationRequest`（逐张）+ `GenerationProfile`（批次级参数集），由 backend 自行决定怎么落地。

```
GenerationProfile   # 批次级，前端可编辑，存在 runs 表
  backend: "launcher_mcp" | "nai_direct" | "comfyui" | ...
  model, sampler, steps, cfg, noise_schedule, effort/model_mode
  uc_preset, variety_plus, decrisp, smea...
  # quality_toggle 固定 false，不暴露给前端
  width, height
  extra: dict        # backend 特有参数，不做强约束

GenerationRequest   # 逐张
  positive, negative     # 已在我们这侧拼接完成的完整串
  seed, count=1
  references[], source_image, characters[]   # 画风线不填

ImageBackend
  capabilities() -> {支持的模型列表/参数范围/是否支持按请求传参/是否需要会话级设置}
  account_status() -> AccountStatus | None   # 只读；不支持的 backend 返回 None
  apply_profile(profile) -> ProfileHandle   # 有状态 backend：写设置并返回原设置快照
  restore(handle)                           # 无状态 backend：空实现
  prepare(request) -> Preparation           # 含 estimated_cost
  submit(preparation) -> Result             # 含 image bytes / path / 实际参数
```

关键点：

- `capabilities()` 决定前端表单。前端不硬编码参数项，而是向 `/api/backends/<id>/capabilities` 要 schema 后动态渲染，这样接本地部署端点时前端不用改。
- `apply_profile` / `restore` 是对「有状态 backend」的让步。Launcher 实现为：批次开始时 `get_generation_settings` 快照 → `update_generation_settings` 写入 → 批次结束或异常时恢复。NAI 直连和 ComfyUI 实现为空操作，参数直接进单次请求。
- 单个 run 绑定一个 profile。改参数要开新 run，不允许中途改，否则数据集参数不一致。
- 画风正负面提示词**不内置**，由前端输入，存在 `runs.style_prompt` / `runs.negative_prompt`；S1 只产出内容段，S2 提交前拼接。
- 默认 profile：V5 标准版（`nai-diffusion-5-full`），其余参数取 Launcher 当前值。
- `uc_preset` 必须暴露给前端且默认设为 None，否则用户输入的负面词会被预设顶掉（实测 effort=medium 下自定义负面词被忽略）。
- `quality_toggle` 固定关闭，不做成可配项。它会往提示词里偷偷追加官方质量词，污染溯源。
- 画风提示词只用于 NAI 出图，不进训练 caption（见 2.2）。
- `account_status()` 是**只读**的额度/订阅展示口子，不参与任何决策。`AccountStatus` 字段全部可选：`subscription_tier`、`anlas_balance`、`fixed_quota_remaining`、`refreshed_at`、`source`（`backend` 或 `local_estimate`）。Launcher 后端若确实没有对应 MCP 工具，则降级返回 `source=local_estimate` + 「剩余预估」（对未完成 source_items 汇总单张 `estimated_anlas`；已发出的不累计、不跨重启保存，docs/08 U2），前端据此标注数据来源，不把估算值当余额展示。

## 2.2 画风提示词的两侧用途（按 2026-10-12 决议）

画风提示词在两侧的角色完全不同，不要混为一谈。

| | NAI 出图侧 | Anima 训练侧 |
|---|---|---|
| 画风部分 | 用户输入的完整画风串（画师名、风格词、权重语法） | **整体替换为单个触发词** |
| 内容部分 | S1 产出的内容段 | 同一内容段，经反推校正后保留 |
| 质量词 | 不加（quality_toggle 关闭） | 不加 |

数据结构上的含义：

- `runs.style_prompt`、`runs.negative_prompt`、`runs.trigger_word` 三者在 S0 一并确定。
- `records.full_prompt_sent` = `style_prompt` + `content_prompt`，仅用于提交和溯源。
- `records.caption_text` = `trigger_word` + 校正后的内容 tag（+ 可选自然语言句），**不含任何 style_prompt 内容**。
- S5 不是「从完整提示词里剔除画风词」，而是「只取内容段，前面挂触发词」。blocklist 退化为一道保险：检查内容段里有没有混入画风词（LLM 精修时可能误加、反推 tag 可能带出画师名），命中就剔除并记日志。
- blocklist 来源：本批次 `style_prompt` 拆出的词 + Danbooru artist/style 类 tag 表。

## 5. 已定决议（2026-10-12）

1. **提示词不内置**：画风正面词与负面词由前端用户输入，存 `runs` 表，S2 提交前与内容段拼接。
2. **生成参数前端可配**：模型、步数、cfg 等全部走 `GenerationProfile`，默认 V5 标准版（`nai-diffusion-5-full`）。接口按 2.1 节设计，前端从 `capabilities()` 动态渲染表单，为本地部署端点留出口。
3. **quality_toggle 不用**，固定关闭，不做成可配项。它是 NAI webui 的「添加质量标签」，开启后会偷偷往提示词尾部追加官方质量词（V5 full medium 实测追加 `very aesthetic, masterpiece, no text`），污染溯源。配套的 `uc_preset`（「不希望的内容」预设）要暴露给前端且默认设为 None，否则用户输入的负面词会被预设顶掉。
4. **画风提示词只用于 NAI 出图**，训练 caption 里这部分整体替换为画风触发词。详见 2.2 节。
5. **WD tagger**：本地已有。产品侧作为可选组件，从源下载不打包。**画风 LoRA 线默认不开启**。显存由产品启动时自动读取（nvidia-smi 或 pynvml），用于决定可用的本地视觉模型。
6. **前端**：确定要做，技术栈 React + Vite + TypeScript，后端 FastAPI（127.0.0.1 + token）。视觉层走设计令牌 + 主题体系，后续做美术精加工。

7. **费用与账号归 Launcher 管**：订阅、令牌、额度都在 Launcher 侧配置，产品不介入，也不再纠结 effort=high 是否免费（由前端配；原「`estimated_anlas` 守卫兜底」已废止，改为 F04 费用提醒，见 docs/05 §7.3）。产品侧只需要一个**只读的账号状态展示口子**，见 F21。
8. **触发词规则**（产品层，非运行时数据）：
   - `runs.trigger_word` 必填，前端输入。
   - 校验一：不得是 Danbooru 已有 tag（会与模型原有概念冲突），建议自造词如 `sty_xxx`。校验走 `search_tags` 或本地 tag 表，命中则警告但允许强制通过。
   - 校验二：不得在本批次 `style_prompt` 中出现。
   - 导出时固定排在 `caption_text` 第一位。
   - 目标画风的 tag 串本身是运行时输入，不是设计期决策项。

## 6. 待讨论

1. **覆盖矩阵的维度与配比** —— 已定方向：**随机 + 字典混合**（字典约束主维度保证覆盖，随机填充其余维度保证多样性），具体设计延后到 F06 模块细化阶段。不阻塞架构：F06 实现的是「读 YAML 矩阵定义 + 统计覆盖度」的机制，维度是配置内容。

   作用：避免数据集内容同质化。若 300 张图里 280 张都是「单人半身正面特写 + 简单背景」，LoRA 会把该构图一起学死。

   候选维度（示例，待定）：

   | 维度 | 取值 |
   |---|---|
   | 人数 | 无人物 / 单人 / 双人 / 多人 |
   | 取景 | 特写 / 半身 / 全身 / 远景 |
   | 视角 | 正面 / 侧面 / 背面 / 俯视 / 仰视 |
   | 场景 | 室内 / 室外 / 纯色背景 / 抽象 |
   | 光照 | 日光 / 夜晚 / 逆光 / 室内灯光 |

   完全交叉 1280 格不现实。实际做法：选 2–3 个主维度做交叉（如人数 × 取景）建立格子，其余维度只约束整体比例（如「无人物 ≥ 15%」「远景 ≥ 10%」）。YAML schema 要同时支持这两种约束。
